# 本專案開發必讀

動這個專案之前先讀完這份。內容是**架構、慣例、以及實際踩過的雷**——
「為什麼這樣寫」「改的時候要守什麼」「哪裡看起來可以改其實不行」。

同一層還有兩份，分工不同：

| 檔案 | 放什麼 |
|---|---|
| `開發必讀.md`（這份） | 規則、架構、踩雷點。**動手前要知道的事** |
| `調校筆記.md` | 量出來的數字、門檻怎麼校準的、個案、量錯過什麼。**當初憑什麼那樣訂** |
| `Block-builders/wwwroot/blueprints/藍圖製作說明.md` | 丟給模型的 system prompt 本體（改它等於改 prompt） |

新增內容前先分清楚是哪一類：數字與個案寫進〈調校筆記〉，不要往這份加。

## 這是什麼

《積木小人 · 世界地標工地》的**後端版**。原本是一包雙擊 `index.html` 就能玩的純靜態
voxel 建築遊戲（`參考/block-builders/`，v1.176.0），這裡用 ASP.NET Core 8 把它架起來，
再加一層 API，把〈藍圖製作說明〉第 7 節那條人工流程**半自動化**：

```
POST generate   描述／參考圖／量出來的主色 → Gemini → 體檢（node）
                  ├ 蓋不起來（有必修）→ 自動重跑，不打擾使用者
                  └ 蓋起來了 → 拍四視圖 PNG（無頭 chromium，9000 塊那一檔）
                       └ 還有「該修的」⚠（東西沒畫上去這一類）→ 自動打磨一輪再拍
                          （塊數偏差那類不算，見〈哪些 ⚠ 值得花錢修〉）
                                     ↓
                       └ 每一份產出（含蓋不起來的）都自動記一筆 history/{stem}.js + .json
                                     ↓
                            使用者看四視圖自己判斷
                              ├ 可以 → ✅ 收進遊戲    寫瀏覽器 localStorage（純前端）
                              │        📁 另存成檔案  POST save → blueprints/ + list.js
                              └ 不像 → POST revise   給意見（可再附圖）跑下一輪
                                          （帶著：目標＋這份藍圖＋報告＋四視圖＋意見）
```

**半自動的分界是刻意的**：蓋不起來有客觀門檻（`fails` 非空），機器判斷得出來就自己修；
「像不像」沒有任何一條檢查看得出來（說明書第 7 節），讓模型自己看四視圖說「夠像了」
只是自我認證，所以那一關交給使用者按鈕決定。`generate`／`revise` **都不存檔**。

`參考/block-builders/` 是**未經修改的上游原版**（自帶 git repo 與一份九千行 README）。
不要改它——它是對照基準。要改遊戲行為改 `Block-builders/wwwroot/` 下的工作副本。
想知道遊戲某段當初為什麼那樣寫，去 grep `參考/block-builders/README.md`（那份的用途就是這個）。

在 repo 根執行（**建置類用 PowerShell 跑，不要用 Bash**，`/flag` 會被 bash 當路徑）：

```powershell

node Block-builders/tools/validate-bp.cjs 某藍圖.js 10000                               # 加驗改量別檔（預設 9000＝四視圖那一檔）
node Block-builders/tools/validate-bp.cjs --names                                      # 列出現有藍圖名字
node Block-builders/tools/shot-bp.cjs 某藍圖.js out.png                                 # 產四視圖（預設 9000 塊那一檔）
node Block-builders/tools/shot-bp.cjs 某藍圖.js out.png 3000                            # 指定檔位（1800／3000／9000）
```

**Gemini 金鑰**：貼進 `Block-builders/gemini.key` 存檔就生效（不必重啟——
`GeminiClient.ResolveApiKey()` 每次呼叫都重讀）。空行與 `#` 開頭的行會忽略。
要用設定值也行（優先於檔案）：`dotnet user-secrets --project Block-builders set "Gemini:ApiKey" "…"`
或環境變數 `Gemini__ApiKey`。**三者都不要寫進 appsettings.json**（那份會進版控）。

**測試**：沒有測試專案，`dotnet test` 無標的。上游有 e2e（`參考/block-builders/tools/e2e-3d.cjs`），
沒有搬過來。要加測試先問使用者放哪、用哪個框架。

## 架構要點

### 藍圖是什麼

一支藍圖 = 一個吃尺度參數 `s` 的 voxel 產生函式，**不是固定模型**：
`gen(v, s)` 每個尺寸都用 `s` 重算一次寬高重畫一次，所以同一座建築可以是 300 塊的小屋
也可以是 10000 塊的大宅。規格全在 `wwwroot/blueprints/藍圖製作說明.md`（620 行）——
**那份文件就是丟給 Gemini 的 system prompt**，改文件等於改 prompt，別在 C# 裡另外寫一份。

### `BlueprintGenerator`：單輪呼叫，不累積對話歷史

`GenerateAsync`（第一版）與 `ReviseAsync`（照意見再一版）都走同一支 `ProduceAsync`：
呼叫 → 體檢 → 蓋不起來就自動重跑（最多 `1 + Gemini:MaxRepairRounds` 輪，預設 4）→
蓋起來就拍四視圖、回傳給人看。

**每一次 Gemini 呼叫都只有一則 user 訊息**（`[new GeminiTurn(false, prompt, images)]`），
不帶前幾輪的來回。一則訊息裡放的就是模型改這一版需要的全部東西：

| 呼叫 | prompt 裡有什麼 | 圖 |
|---|---|---|
| generate | 目標（描述 ＋ 參考圖量出來的主色） | 參考圖（最多 4 張） |
| revise | 目標 ＋ 目前這份藍圖全文 ＋ 它的體檢報告 ＋ 使用者意見 | 參考圖（可多張）、四視圖、使用者補的圖（順序與編號在 prompt 裡有標） |
| 自動重跑 | 目標 ＋ 壞掉那份全文 ＋ 體檢報告／錯誤訊息 | 無（修程式錯誤用不到圖） |
| 自動打磨 | 同 revise，但「使用者意見」那一段換成報告裡的 ⚠ 清單 | 同 revise |

**唯一跨得過輪次的東西是程式碼本身**——所以說明書第 5 節那幾行開頭註解
（正面／側面／三樣識別物／部件清單）是必寫的，後端補充第 6 條也再講一次。
那是下一輪的模型唯一看得到「這一版原本打算做什麼」的地方；沒有它就會愈改愈偏
（改了握把、順手把杯口厚邊拿掉）。註解是合法 JS，`new Function` 照跑。

**`Candidates`＝第一版並行叫幾次，預設 1（關掉）。** 曾經預設 3，被使用者否掉，
理由是對的：**機器挑不出哪個比較像**——後端只能照「提醒最少」排，而提醒多寡跟像不像
幾乎無關，所以預設顯示的那個等於隨機挑，比較的工作全推給使用者，成本卻是 3 倍。
而第二輪之後使用者的意見（「握把太小、杯口厚邊不見了」）比重擲骰子有用得多，
那條路一次只花一次呼叫。

機制留著沒拆（設 2 以上就會並行跑、前端也會擺出那一排讓人挑）：候選之間完全獨立，
所以直接 `Task.WhenAll`；四視圖那一段有 `BlueprintShooter.Gate`（semaphore 2）擋著，
不然會同時開三四個 chromium 各自軟體算 WebGL，每一張反而更慢。
`Angle()` 那三段取向也只在 `Candidates > 1` 時才會加。

**`PolishRounds`（預設 1）只在 `Candidates == 1` 時才會做**——也就是預設會做：
蓋起來但**還有「重要」等級的 ⚠**（`check.Important`，見下一節）時自動再修一輪。
這一輪比「再抽一個樣本」划算，因為它修的是**客觀查到的缺陷**（窗戶落空、碎塊飄著、
部件太少），不是重擲骰子。既然錢都付了，那一輪會把整個 `Fixable` 一起請它修。
打磨完**沒有更好就留原本那一版**，多跑一輪不該讓結果變差。
這跟「讓模型自己說夠像了」不是同一件事：它不判斷像不像、也不會提早收工。

不累積歷史的理由：token 貴，而且舊版的程式碼會干擾它——把好幾版都帶上，它會把
上一版已經修掉的東西改回來。所以「要改的那一份」永遠是明確寫在這一則訊息裡的那一份。

system prompt = 〈藍圖製作說明〉全文 ＋ 後端模式補充（附現有藍圖名字清單避開撞名、
要求改版時**沿用同一個 name**、講明每次呼叫都是獨立的、要求寫開頭註解、告知四視圖的檔位）。

**說明書裡「後端用不到」的段落是剝掉、不是用文字覆寫的。** 那份文件同時給人看
（人工流程還在用）。做法是在 `.md` 裡用 `<!-- 後端不送 -->` … `<!-- /後端不送 -->` 包起來，
`BlueprintStore.ReadPromptDocAsync()` 送出前剝掉（`StripHumanOnly()`）。
**剝掉比覆寫好**：互相矛盾的指令比沒有指令更糟，模型會照著去叫一個不存在的玩家做事。
標記不成對時整段留著——寧可多送一段，也不要因為打錯一個標記就吃掉半份說明書。

現在有 **7 對**標記，剝掉 3,303 字元（全文的 14.8%）。分兩類：

| 剝掉什麼 | 大小 | 為什麼後端不需要 |
|---|---|---|
| §0 的安裝提醒、§7 的「怎麼拿報告」、§8 最後兩項、**§5 第 6 項**、§7 的「請玩家再跑一次」 | 約 1,100 | **教玩家轉手的步驟**。§5 第 6 項與那句「請玩家再跑一次」是後來才抓到的漏網——它們直接跟後端補充第 2 條打架（那條寫著「不要叫玩家開 `藍圖預覽.html`」） |
| §7 的整份範例報告（含三張輪廓 ASCII） | 約 1,650 | 模型**從不產報告、只讀報告**，而 revise／修復輪每次都附一份真的。留下來的「怎麼讀」表格才是有用的那半 |
| 附錄〈字元圖 `layers`〉 | 約 550 | 它教一條路再叫模型不要走。**後端不需要知道這個選項存在**——不講它就不會用 |

順手也把文件裡重複三到五次的幾句合併掉（「`box`／`cyl`／`taper` 只能軸對齊」原本
在 3.3 出現兩次、§5 再一次；「分兩段就看得出是彎的」兩次）。

**這些省不到錢，是清理指令。** 說明書走隱式快取打一折，而快取後的輸入單價是輸出的
1/50——整份兩萬字的說明書，價錢等於 260 個輸出 token。砍 15% 大約省一次呼叫的 1%
（冷啟動那一次例外，那時它是全價）。值得做的理由是矛盾與雜訊，不是帳單。

**還沒動、但是最大的一塊**：§4.1 小教堂範例佔全文 15.7%，而它是建築——13 筆真實使用裡
只有 1 筆是建築，其餘是角色、動物、器物。但它同時是「細節密度＝十四個部件」的唯一錨點，
動它會直接改變產出的複雜度，要改得單獨跑對照（現在紀錄有 `usage` 與 `think`，比得出來）。
§4.2 圓塔（3.3%）示範的 `arch`／`windowGrid`／`taper` 小教堂都有，獨有的只有中空 `cyl`。

`revise` 的細節：
- **prompt 要附上一版的部件清單，並明講「這張清單上每一項都必須還在」**（`PartsLine()`）。
  實測四組 revise（公司大樓、雙子塔、大坂城、雙層巴士）**每一組都改壞了沒被要求改的地方**：
  整排側窗變成只剩車尾一段、屋頂平白多一圈簷口、裙樓從過高變成扁平貼地、下層面寬無故縮窄。
  **而且送 2 條跟送 6 條一樣壞**——所以瓶頸不是意見太多，是「每輪重吐整份 8 KB 藍圖」時
  沒有任何東西在守舊的部件（這份文件本來就寫著「**沒有任何一條檢查抓得到它把東西拿掉了**」）。
  說明書第 5 節要模型寫的那行「部件：…」剛好就是現成的對帳單，拉出來明講。
  **這一條還沒驗出有沒有效**，只驗了那段話真的送得進 prompt。
- 報告**當場重驗**，不吃前端傳回來的——前端那份可能是上一版的，而報告要跟程式對得上
- 四視圖優先用前端傳回的 `shotUrl` 讀檔（省下重拍的 8 秒），檔案不在才重拍。
  那個 url 是前端給的，所以 `BlueprintShooter.TryLoadAsync()` 只取最後一段檔名、
  而且要求解出來的絕對路徑真的落在 `shots/` 裡（防目錄穿越）

### 參考圖可以給到 4 張

`image` 這個 form 欄位**可以重複給**（前端 `refImgs[]` → 後端 `List<IFormFile>`），
`generate` 與 `revise` 都是；上限寫在 `BlueprintsController.MaxRefImages`。

**一張不夠。** 說明書第 5 節第一句就要模型講出「正面看是什麼形狀、側面看是什麼形狀」，
只給一張正面照的話**側面是它自己編的**（個案見〈調校筆記〉4）。

- 上限 4 的理由：一張 HIGH ＝ 1,120 個 token（約 US$0.0008），四張加起來不到一次呼叫的 4%，
  所以成本不是問題；設上限只是不要讓人一次拖 20 張進來。**超過直接擋、不要靜靜砍掉**，
  不然使用者會納悶模型為什麼沒看到側面那張。
- prompt 要**講明那幾張是同一個目標**（`Goal()` 的 `refCount > 1` 分支）——
  不講的話它會當成幾個不同的東西。
- `RevisePrompt()` 的圖片編號要**數圖不是數句子**：參考圖好幾張會擠在同一句
  （「第 1–3 張是參考圖」），拿 `which.Count` 當序號會讓後面全部錯位。
  實測 revise 一次送 5 張：3 張參考圖（HIGH）＋ 四視圖（ULTRA_HIGH）＋ 補充圖（HIGH）。
- **主色是所有張一起量的**，不是各張各量再合併（那樣會挑出一堆重複色，而且各張的
  數量沒得比）。所以 `topColors()` 拆成 `binOf()`（一張一份色桶）＋ `pickColors()`
  （把所有張的桶加起來一次挑）；每張都取樣 64×64，所以原圖大小不影響權重。

### 參考圖的主色：量的是「面積」，不是「認得出來的顏色」

前端上傳圖的時候順手量一份主色（`藍圖產生器.html` 的 `topColors()`），文字送給模型。
起因是說明書只叫模型「抓圖片的 4–6 個主色」而沒有任何東西驗證它抓對——
實測皮卡丘的黃變成橄欖黃、樹懶變成水泥灰。

**它量的是「面積」，所以面積小卻一眼認得出來的顏色（屋瓦、招牌、蝴蝶結）永遠量不到。**
第一版沒有處理這件事，兩個地方都要顧：

- `topColors()` 從**所有夠大的桶**由多到少一路往下挑（不是只看前 n 名），
  而且要求彼此距離 ≥ `COLOR_MIN_GAP`（RGB 歐氏距離 40），太小的桶（`COLOR_MIN_SHARE`）跳掉。
  **只照數量取前 n 名會挑出「同一片顏色的 n 個鄰居」**——一大片白牆或草地會攤在
  好幾個相鄰的桶裡，把名額佔滿（數據見〈調校筆記〉3）。
- **挑不滿就給少一點。** 整張圖真的只有兩個色系時，說 2 個比湊 8 個假的誠實。
- `BlueprintGenerator.Goal()` 只能說「**主體**照這幾個色」，不能說「`pal` 就從這幾個色挑」。
  **兩條要一起改**——照片本來就是單色（陰天、黑白照）時，光修演算法還是灰的。

### 四視圖：無頭 chromium 開真正的預覽頁

`tools/shot-bp.cjs` 用 playwright 開 `file://` 的 `藍圖預覽.html`、填 `#paste`、按 `#load`，
再按它自己那顆 `#shot`（下載四視圖），用 `page.on('download')` 把檔案接下來。
**所以拿到的圖跟玩家手動按出來的逐像素同一張。**

不自己畫的理由：`shotPng()`（`藍圖預覽.html:473` 起）裡有一堆實測換來的取景細節——
正面必須站在 −z（鏡頭預設站背後，拍回去會把正背面弄反）、每一格各自量 x／z 半寬取景
（共用 `fitCamera` 的話主體只佔兩成畫面）、俯視 `pitch` 上限 1.45、45° 的厚度只取 0.55 倍、
每格 render 完要**在同一個工作裡** `drawImage`（WebGL 的 drawingBuffer 合成後就被清空）。
重畫一份等於把這些坑再踩一輪，而且產出的圖跟玩家看到的不一樣。

- **playwright 不是這個專案的相依**，是機器上已經有的（`@playwright/mcp` / `@playwright/cli` 帶的）。
  找法照上游 `tools/e2e-3d.cjs` 的解析順序（`%APPDATA%/npm/node_modules/...`）。
  `chromium.launch()` 不必帶任何參數，headless 用 SwiftShader 就跑得動 WebGL。
- 用 `file://` 開而不是連自己的站台：預覽頁本來就設計成 `file://` 能用，這樣產圖不必先起站台。
- **拍的是 `Gemini:ShotSlots`（預設 9000）那一檔**，不是預覽頁自己的預設 3000。
  說明書第 6 節寫著「上萬塊正是看得出像不像的那一檔——招牌、窗框、雕花在三千塊時
  只是幾個色塊」，而 9000 也是遊戲面板的最大檔。實測：皮卡丘在 3000 塊沒有手腳、
  五官糊成一片，那有一部分只是在看它最不利的那一檔。
  切檔位就是按預覽頁自己那三顆按鈕（`#cnt button[data-v="9000"]`，handler 是同步的
  ——`wantCnt → syncSeg → build`，所以 click 回來時場景已經重蓋好了）。
  面板只有 1800／3000／9000 三檔，給別的數字會退回預設檔並在 `tierNote` 講出來。
- 一次拍會產**兩個檔**（都在 `wwwroot/shots/`，放 wwwroot 底下才能在產生器那頁直接顯示）：

  | 檔案 | 尺寸 | 給誰 |
  |---|---|---|
  | `{目標}/xxx.png` | 1024×1024，約 1.1 MB | **人**：產生器頁顯示、預覽頁下載 |
  | `{目標}/xxx-ai.jpg` | 同尺寸的 JPEG，約 170 KB | **模型**：`inlineData` 送這一份 |

  分兩份是**省上傳位元組，不是省 token**（見〈成本的形狀〉）。約 8 秒。
  **會累積，要清就直接刪那個資料夾。**
  舊的（這個機制之前產的）沒有 `-ai.jpg`，`ReadAiCopyAsync()` 會退回送 PNG——
  一樣的畫面、一樣的 token，只是上傳大一點。
- 拍不出來時 `TryShootAsync` 回 null 而不是丟例外：四視圖是加分項，不該讓整條產生流程掛掉
  （那時前端會說「只能看報告裡那三張字元輪廓圖」）。

### 四視圖的顏色不能拿來評色（實測差很遠）

**圖上的顏色 ≠ 藍圖 `pal` 宣告的顏色。** 四視圖是在遊戲場景裡拍的，那個場景有偏青藍的
天光、**草綠的地面反光**（`engine.js:734` 的 `HemisphereLight(0xd8ecff, 0x5b7a48, 1.25)`）
與一層淡青藍的霧（`engine.js:730` 的 `Fog(0xbcd3e0, 90, 320)`）。實測一份
`pal[0] = '#fcda78'`（亮黃，佔 96% 的格子）的皮卡丘，圖上量到的是 `#838b7a`——
**飽和度 95% → 7%**（完整數字與量法見〈調校筆記〉6）。

**這是遊戲的美術風格，不是 bug**（48 座內建藍圖都在這個環境下呈現），所以沒有動它。
但它對產生器有三個後果：

- 使用者看四視圖判斷「像不像」時，**顏色那一維的依據是失真的**——一隻 `pal` 完全正確的
  皮卡丘，在圖上就是橄欖綠的
- revise 時模型看的是同一張圖，它會去改**本來正確的** `pal` 來補償。那正是這份文件
  到處在防的事（「逼模型去修沒壞的東西，換來的是它把對的地方改壞」），
  而且在顏色這一維是**每一輪都在發生**
- 補償的方向是**發散**的：調得更飽和 → 渲染後還是灰 → 下一輪再調 → 離參考圖越來越遠

所以**任何「拿四視圖評顏色」的功能都不要做**——自我對照那一輪的 prompt 因此明文禁止
談顏色（`BlueprintGenerator.CompareAsync`）。要驗顏色只剩兩條路：比程式碼裡的 `pal` 與
`refColors`（不看圖），或改拍照當下的光照。兩條都還沒做，見〈調校筆記〉6 最後一段。

> 〈調校筆記〉4 中正紀念堂那筆「整棟是灰的」，當初歸因於 `refColors` 量到 8 個灰
> ＋ prompt 綁死 `pal`。那個歸因**不完整**：就算主色量對了、`pal` 也寫對了，畫出來一樣會灰。

### 自我對照：一版蓋出來之後，拿它自己寫的設計去對帳

說明書第 5 節第 6 項是整份文件裡**唯一的「像不像」驗收步驟**（「請玩家照第 7 節跑一次
診斷，把報告與畫面截圖一起貼回來……不夠像就調係數、補部件再來一次」），而後端模式
把它**剝掉了**（見上面那張剝除表）。**剝掉之後一直沒有東西接手**——自動打磨只在有
「重要」⚠ 時才觸發，而那幾條全是客觀缺陷（窗戶落空、碎塊飄著、部件太少），跟像不像無關。
實測一份尾巴不是閃電形、腮紅大了一圈的皮卡丘，體檢結論是「沒有必修、沒有提醒」
（個案見〈調校筆記〉6）。

所以 `BlueprintGenerator.CompareAsync` 在**整條鏈的最後**（打磨之後）再叫一次：
拿這一版**開工時自己寫下的那幾行註解**（正面／側面／三樣識別物／部件清單）與參考圖，
逐條比對剛拍好的四視圖，列出「說好要有、但圖上看不到或明顯不一樣」的地方。

**它不改任何東西**，只產一份清單顯示在產生器頁上（`#diffBox`），旁邊那顆
「📝 拿這幾條去改一版」把清單**填進意見框**——**不會自己送出**。這是刻意的：
清單是模型自己列的，採不採用、要不要先改幾個字，是使用者的判斷。
所以它跟「讓模型自己說夠像了」不是同一件事：它不判斷像不像、不會提早收工、也碰不到程式。

七個實作上的決定：

- **明文禁止評顏色**，理由見上一節。這一輪最容易做錯的就是這裡。
- **只在 `Candidates` ＝ 1 時做**。清單只對得上一份藍圖，多候選時擺一份在旁邊會誤導，
  成本也要乘候選數。
- **前端切換候選時要把 `diff` 清掉**（`useCandidate()` 裡跟 `inGame`／`inFile` 一起歸零）。
  打磨前／打磨後那兩份也是候選——清單是對「打磨後」那一份做的，切回去之後它講的東西
  就對不上，**留著比沒有更糟**。
- **system prompt 不送〈藍圖製作說明〉**，自己一份一百多字的。這一輪的工作是看兩張圖對帳，
  用不到藍圖 DSL 的規格，而那兩萬多字全是「怎麼寫藍圖」的指令，對這一輪是雜訊
  （而且實測快取一直沒命中，那是全價的一萬五千個 token）。
- **失敗要吞掉**（`InvalidOperationException`／`HttpRequestException`），跟 `TryShootAsync`
  同一個原則：藍圖這時已經產好、拍好、也寫進紀錄了，不能讓一個加分項把整輪打掉。
  **但取消例外不吞**——那是使用者按了停。
- **要寫進產生紀錄**（`BlueprintHistory.UpdateDiffAsync` 事後補寫那一筆的 `diff`，
  所以 `BpCandidate` 要帶著自己的 `Stem`）。**這一條第一版做反了**：當初的理由是
  「採用了就會以 `feedback` 的形式進下一筆紀錄，沒採用等於使用者判斷它不對」——站不住。
  第一次真跑（皮卡丘）就是 generate ＋ 自動打磨、使用者還沒 revise，
  **清單完全沒落地**；而要判斷「對照輪到底有沒有用」，要比的正是
  「它說了什麼」與「圖上實際怎樣」。清單只活在產生器那一頁的 JavaScript 裡、
  關掉分頁就沒了——那正是〈產生紀錄〉整節在解決的事，在同一個地方犯第二次。
  補寫而不是一起寫的理由見那支的註解：對照輪比紀錄晚跑（它要等整條鏈含打磨都結束），
  等它跑完再一起寫的話，它掛掉就連藍圖都沒存到。
- **圖片編號要數圖不是數句子**（跟 `RevisePrompt` 同一個坑）。0 張參考圖時那句「拿設計
  與參考圖比對」也要換掉，不然它會去找一張不存在的圖。
- **清單在頁面上是一條一列 ＋ 勾選框，預設只勾前兩條**（`renderDiff()`）。
  實測六條原封不動一起送出去改一版：**一條都沒修好**，還平白多出一圈屋頂簷口
  （見〈調校筆記〉7）。但**哪一條最不像是使用者勾的，不是機器砍前 N 條**——
  清單的順序是模型自己排的，它排第一的那條可能根本做不出來（實測「中央八角切角」就是），
  機器砍前兩條等於把額度浪費在做不到的事情上。
  拆行規則：取 `·` 開頭的行（實測四組 23 條都是這個格式），一條都拆不出來就整段顯示
  （例如它只回「都對得上」）。送出時前面加一句
  「這一輪**只改下面這幾條，其餘一個字都不要動**」——照 `PolishAsync` 那句抄的，
  revise 原本只有比較軟的「使用者沒提到的地方不要順手改掉」，而那圈屋頂簷口就是它不夠硬的證據。
  **這一條還沒驗出有沒有用**：要拿同一份藍圖、同一份清單跑「一次送 4 條 vs 一次送 2 條」
  的 A／B 才知道，而「條數太多」本來就只是假設之一（另一個同樣說得通的解釋是
  「每輪都要重吐整份 8 KB 藍圖」）。
- **四視圖的左右要在 prompt 裡講明，不然它會報出假的差異。** ①正面格是站在藍圖正前方
  （−z）往回看的，所以**畫面左邊才是 `+x`**＝藍圖自己的右手邊。不講的話它會把
  「招牌畫在右側（`+x`）、圖上出現在畫面左邊」當成缺陷報出來——實測**連報兩次**
  （第一版一次、改版後又一次），每次吃掉六條額度裡的一條，而那一條會叫模型
  把一個本來正確的東西搬到錯邊。
  實證：`公司大樓測試2` 的 `signX = totalW/4 + 1`（正數＝`+x`），正面格上那道紅招牌
  就在畫面左邊；②右側格的畫面右邊則是 `-z`（同一張圖的右下角看得到招牌側緣）。
  順帶一提**報告裡那三張 ASCII 輪廓圖的左右跟四視圖相反**（①把 `+x` 印在右邊，
  等於站在背後看），所以那兩種圖不能用同一套左右去讀。
- **這一輪的 `goal` 不能帶 `refColors`。** 產生輪的 `goal` 裡有「主體的顏色照這幾個來」
  一整段，而這一輪的規則是「顏色完全不談」——兩段擺進同一則訊息就是**互相矛盾的指令**，
  比沒有指令更糟（跟說明書剝除那一段同一個原則）。所以 `CompareAsync` 自己組一份
  `Goal(description, refCount, null)`，不沿用呼叫端那一份。第一版沒注意到，
  是拿 stub 驗「prompt 裡到底寫了什麼」才抓到的。

還有一支 **`POST compare`（只跑對照）**：拿一份現成的藍圖與它的四視圖跑對帳，
不產生、不打磨、不存檔——跟 `POST validate`（只體檢）、`POST shot`（只拍照）同一類的單件工具。
給 `stem` 就從產生紀錄跑（程式、四視圖、描述都在裡面，清單也會補寫回那一筆），
否則吃 `code`／`shotUrl`／`description`。**兩條路都沒有參考圖**（紀錄裡沒存、這支也不收上傳），
所以它對的是「它自己寫下的設計」與「它自己畫出來的圖」——那正是對帳的主軸
（識別物在不在、部件漏了沒），但看不出「跟真正的目標像不像」。
沿用現成的四視圖所以只花一次便宜呼叫，適合回頭對舊產出補跑。

**還沒驗的那一半**：以上都是拿假端點驗的——送出去的請求長什麼樣（system 131 字、
帶 1 張 `ULTRA_HIGH` 的四視圖、註解四行抽對）、前端顯示與那顆按鈕（0 個 page error）。
**清單本身的品質只有真金鑰跑得出來**，`CompareThinkingLevel` 要不要降到 low 也是。
照老規矩：stub 能驗的是「送出去的請求長什麼樣」，**不能驗「Google 回什麼」**。

### 成本的形狀（**縮圖省不到 token**，這條之前寫錯過）

**Gemini 3 的圖片是按 `mediaResolution` 固定計價的，跟像素多少、檔案多大都無關**：
LOW 280、MEDIUM 560、HIGH 1120（不指定時的預設）、ULTRA_HIGH 2240 個 token／張
（[官方文件](https://ai.google.dev/gemini-api/docs/generate-content/media-resolution)）。
所以「把圖縮小來省 token」在這個 API 上不成立——**縮了一個 token 都省不到，只會讓模型
看不清楚**。這裡曾經照 Gemini 2.x 的切塊模型把四視圖縮成 768（每一格只剩 384²），
那是白損失細節，現在改回原生 1024。

**按輸出計價的那一半（輸出＋思考）是大頭，而思考通常比輸出還多。**
所以能省的是這三個，不是圖片：

1. **思考強度**（最貴的旋鈕，分三格調，見〈思考分級〉）。
2. **`systemInstruction` 要每輪逐字相同**——`BuildSystemPromptAsync` 的輸出**必須穩定**，
   不要把時間、亂數、每次不同的敘述塞進去，隱式快取才有機會命中。
   **但實測 `cached` 一直是 0**（見〈調校筆記〉1.3），所以目前說明書是全價，
   瘦說明書是真的有效的，別再照「它打一折」去推算。
3. **呼叫次數**：`Candidates` 與 `PolishRounds` 直接乘上去；自動重跑那幾輪最貴
   （`RepairThinkingLevel` 是 high）。

`usageMetadata` 每次都會解出來寫進 log，也回給前端顯示（「這一次呼叫 3 次｜輸入 64,500
（快取命中 59,400）｜…｜估 US$0.0578」），**而且會寫進那一份的產生紀錄**
（`HistoryHead.Usage` ＋ `Think`，見〈產生紀錄〉）。**估的**，帳單以 Google 為準；單價寫在
`appsettings.json`（優惠價到 2026-12-31，之後翻倍）。

圖還是會轉一份 JPEG 送（`-ai.jpg`），但那是**省上傳位元組**（1.1 MB → 約 170 KB），
不是省 token；`ImageMaxPx` 預設 1024 ＝ 四視圖原生尺寸，等於只換編碼。
使用者上傳的圖在瀏覽器縮到長邊 1024（`prepImage()`），理由一樣是上傳時間。
兩邊都不必裝影像套件——一邊是本來就開著的 chromium，一邊是瀏覽器自己的 canvas；
轉不動就退回原檔。

### 沒有金鑰時怎麼測整條流程

架一個假的 Gemini 端點頂上去——`Gemini__BaseUrl` 指過去、`Gemini__ApiKey` 隨便填：

```powershell
$env:Gemini__BaseUrl = "http://localhost:8791"; $env:Gemini__ApiKey = "test"
```

那支 stub 收 `POST /v1beta/models/{model}:generateContent`，回
`{"candidates":[{"content":{"parts":[{"text":"```js…```"}]},"finishReason":"STOP"}]}` 就行。
**再回一份 `usageMetadata`**（`promptTokenCount`／`cachedContentTokenCount`／
`candidatesTokenCount`／`thoughtsTokenCount`），不然前端那行成本會顯示 0。

讓它第一次故意回一份漏參數的壞藍圖，就驗得到自動重跑；回一份「提醒多」再回一份
「提醒少」，配 `Gemini__Candidates=1` 就驗得到自動打磨；把收到的請求存檔（記得把
`inlineData.data` 換成長度摘要，不然幾 MB 沒辦法看）就驗得到 prompt 裡到底放了什麼、
`thinkingConfig` 與 `mediaResolution` 有沒有照設定送出去。

實測跑過的：generate 2 輪（壞→自動重跑→好）、revise 帶 3 張圖單輪過關、
`Candidates=3` 並行 31 秒三張圖不撞檔名、打磨那一輪比較過 `Warns` 後正確地留原版、
用 playwright 開真的產生器頁確認候選那一排點得動、成本那一行算得對、0 個 page error。

### 為什麼體檢要叫 Node，而不是在 C# 重寫

`src/blueprints.js:5003` 有 `module.exports`，同一支檔在瀏覽器與 Node 都能跑。
`checkBlueprint()`（`:4802`）就是遊戲裡「🔍 檢查藍圖」那顆按鈕背後那支，
`importBlueprint()`（`:4690`）已經處理好剝 ```js 圍籬（`cleanPaste`）、抓 `// 檔名：`
（`bpFileName`）、撞名自動編號、把語法／執行錯誤翻成人看得懂的訊息。
**在 C# 重寫任何一段就等於讓報告跟說明書第 7 節對不上。** 驗證器只做接線。

踩雷點：`importBlueprint` 內部用 `new Function('customBlueprint', code)` 建 `gen()`，
那個閉包的作用域鏈只有「`customBlueprint` 參數 → global」，所以 `dim`／`tint`／`paintFrom`
這些工具**一定要掛上 `globalThis`**（`validate-bp.cjs` 開頭那個迴圈），
不然 `gen()` 一跑就 `ReferenceError`。

### 後端加驗：把「不像」變成量得出來的東西

`checkBlueprint()` 是遊戲與預覽頁共用的，門檻拿內建 48 座校準過，刻意只留「真的是缺陷」
的那幾條。**`validate-bp.cjs` 另外在報告尾巴加七條**（只加在後端這份，上游那支不動）：

**加驗量的是「四視圖拍的那一檔」（`Gemini:ShotSlots`，預設 9000），不是 `BP_TARGETS`
最後那一檔。** 由 `BlueprintValidator` 當第二個 argv 傳給 `.cjs`（沒收到就退回 9000）。
理由：加驗就是要把「像不像」變成量得出來的東西，而「像不像」是看那張圖判斷的——
量的檔位跟拍的檔位不同，評的跟看的就不是同一個東西。實測 48 支有 2 支結論會對不上，
而且兩個方向都出現過（圖上有缺陷但報告說沒事、報告報了圖上沒有的缺陷），
數據與門檻重掃結果見〈調校筆記〉2.6。`checkBlueprint` 自己那四檔不受影響。

| 加驗 | 抓什麼 | 憑什麼 |
|---|---|---|
| `windowGrid`／`tint`／`paintFrom` 落空 | 那個部件**其實不存在**，但塊數與配色都很漂亮 | 這三支都是「牆不在那裡就什麼都不做」，不報錯（說明書 3.3、`paintFrom` 方向那段） |
| 左右對稱度 | `mirrorX` 只鏡射起點（兩隻手臂指向同一邊） | 只報數字不示警——建築有不對稱翼樓、動物有姿勢 |
| 懸空的小碎片 | 爪子離手、尖端離頂差一格 | 只在「≤4 組且最大那組 ≤12 格」時示警；組數多或體積大是故意的（倫敦眼的輻條） |
| 畫圖呼叫數 | 部件太少＝看起來是個盒子 | 說明書兩處寫「像不像幾乎全靠部件數」，卻沒有一條在數 |
| 宣告了卻沒出現的顏色 | 那個部件被後寫蓋掉、或根本沒畫 | 現有報告只查反方向（用到的索引超出 `pal`） |
| **只有一面有花紋** | 窗格／飾條／五官全畫在朝 −z 那一面，側面與背面是空白牆 | 見下 |
| **大檔位反而看不到** | 表面裝飾在小檔位露在外面，換到大檔位被後畫的量體整個包進去 | 見下 |

後面那兩條的量法與門檻（門檻要動就得重掃一次，數據在〈調校筆記〉2）：

- **只有一面有花紋**＝那一面的可見表面上「相鄰兩格顏色不同」的比例。
  **不要改用「表面有幾種顏色」**，那分不出來——空白側牆照樣有基座、女兒牆好幾個色。
  示警條件「最花那一面 ÷ 其餘三面平均 ≥ 4」。角色動物的正面本來就比背面花，
  門檻訂在 4 是為了不誤報它們。
- **大檔位反而看不到**＝比 3000 檔與**四視圖那一檔**「露在外面的格數」：格數長 ≥2 倍
  而可見格數只長 ≤1.3 倍。**用比值不用絕對值**，格數本來就會跟著尺度長。
  存在 ≠ 看得見，而現有報告從頭到尾只數格數（連「300 塊時各色還在不在」也是），
  所以這種缺陷在報告上完全隱形：塊數漂亮、配色齊全、連通性滿分。
  修法指名 `tint`／`paintFrom`——裝飾疊一塊實心的 `blob`／`box` 上去會被後畫的部件蓋掉。

實作上的四個坑（都實際踩過）：

- **加新檢查要順便想「它進得了 `important` 嗎」。** 只放 `fixable` 的檢查
  **永遠不會自己觸發打磨**，等於白做。0 誤報的檢查就該放 important。

- **計數器要在所有 `fitScale`／`makeBlueprint` 之後才 reset。** 那幾支內部是**掃描**，會把
  `gen()` 跑幾十次；不 reset 的話數出來的是幾十輪、各種尺度混在一起的總和
  （金閣寺被數成 130 次 `windowGrid`，真正的答案是 2 次）。
  **這個坑踩過兩次**——第七條加驗要多跑一次 3000 檔的 `fitScale`，也必須壓在 reset 前面。
- **鏡射軸要自己找，而且要從質心找起、不是包圍盒中心。** 一個伸出去的握把（或尾巴、翅膀、
  伸長的手）會把包圍盒拉歪一大截：杯身在 x=0、握把伸到 x=24 的馬克杯，包圍盒中心在
  x≈5.5，在它附近掃 ±4 永遠碰不到真正的中軸——量出來 39%，而同一時間 `馬克杯.js` 是 95%，
  **兩個數字互相矛盾才發現的**。改成從質心掃 ±12（質心受小握把的影響小得多）：
  同一份從 39% 變 90%、軸正確找到 x=0。現在馬克杯 95%、金閣寺 97%、扇形車庫 88%、
  小教堂與大佛 100%。
- **加驗要插在「結論」那一行之前，而且結論要重算。** 直接接在後面的話報告會先寫
  「結論：沒有必修、沒有提醒」再列出一串 ✘，模型讀到的是自相矛盾的兩段話。
- 只攔 `globalThis` 上那一份就好：`blueprints.js` 內部的 `windowGrid` 呼叫的是模組作用域裡的
  `tint`，攔不到——**剛好就是我們要的**，數到的都是藍圖自己直接下的那幾筆。

一律走 `warns` 不走 `fails`：`fails` 會觸發自動重跑，而其中幾條是「大概錯了」而不是
「一定錯了」（部件偏少、對稱度低都可能本來就長那樣）。逼模型去修沒壞的東西，
換來的是它把對的地方改壞——那正是這份報告最初就在避的事。

### ⚠ 分三層（`warns` ⊃ `fixable` ⊃ `important`）

`validate-bp.cjs` 除了 `warns` 還吐兩個子集。**分層只決定「要不要主動花一次呼叫去修」**——
三層都照樣寫進報告全文給人看、也給模型看。實測 28 支現有藍圖共 16 個 ⚠：

| ⚠ 的種類 | 次數 | 分層 | 自動打磨 |
|---|---|---|---|
| 東西沒畫上去（`windowGrid` 0 格／`tint` 全落空／`paintFrom` 落空） | 2 | **重要** | 自己就會觸發 |
| 有小碎塊飄著 | 1 | **重要** | 自己就會觸發 |
| 部件偏少（畫圖呼叫 < 8 處） | 0 | **重要** | 自己就會觸發 |
| **只有一面有花紋** | 0（產出裡 1） | **重要** | 自己就會觸發 |
| **大檔位反而看不到** | 1 | **重要** | 自己就會觸發 |
| 宣告的顏色沒出現 | 3 | 普通 | 不自己觸發，但跑了就順手修 |
| 最底層太少格 | 0 | 普通 | 同上 |
| 塊數偏差 — **頂到 `lo`／`hi`** | 10 | 普通 | 同上 |
| 塊數偏差 — 純階距 | 0 | **不修** | 連提都不提 |
| 產生時間太久 | 0 | **不修** | 同上 |

分層是使用者排的（「東西沒畫上去、小碎塊飄著這兩種重要，宣告顏色沒出現普通」）。
`部件偏少` 也放重要：說明書兩處寫「像不像幾乎全靠部件數」，而實測產出裡
「皮卡丘沒有手腳」就是這一條。

**塊數偏差要分兩種，修法完全不同**（原本一律不修，那是錯的）：

- **純階距太大** → 報告給的修法是「把跳最兇的那個維度**係數**調小」，而〈藍圖製作說明〉
  第 5 節寫著「**係數之間的比例就是這棟建築的長相**」——為了追一個數字去改係數，
  換來的是它變得更不像。玩家設 3000 拿到 1769 塊只是小一點。**這一種不修。**
- **`s` 頂到 `hi`／壓到 `lo`** → 修法是「調 `lo`／`hi`，或把各部件的**下限**（`dim` 第三個
  參數）改小」，**完全不動係數比例**，所以**這一種要修**（普通層，跑了打磨就順手一起）。
  症狀是玩家挑小檔位永遠拿到一棟塞不下的樓。28 支現有藍圖有 10 支屬於這一種。

分得出來的方法：`checkBlueprint` 把修法寫在報告裡那一階的**下一行**，比對那一行就知道
是哪一種——warn 字串本身只有「1600 塊偏差 133%」，看不出差別。

打磨的 prompt 因此要講清楚是**係數**不能動，不能再寫「塊數的事都不用管」——
清單裡現在會出現塊數偏差，兩句話會打架。

實作細節：

- 分層用字串比對（`產一份要` 排掉、`塊偏差` 看報告那一行分兩種；重要那層比對
  `windowGrid|paintFrom|tint 全部|飄在旁邊|畫圖呼叫|那一面有花紋|大檔位反而看不到`），
  寫在 `validate-bp.cjs` 併結論那一段。
- prompt 分兩段列出來（「### 一定要修」／「### 順手一起修」），讓它知道先後。
- **「有沒有更好」先比重要的、同分才比普通的**：只修掉普通那項而重要那項還在，
  不該算成功——不然它會用「把 `pal` 拿掉一色」換掉「窗戶沒畫上去」。
- 效果：28 支現有藍圖只有 **4 支**會觸發打磨，其餘省掉那一次呼叫（名單見〈調校筆記〉2.4）。

> 這幾條上線第一天就抓到一個**現有藍圖的真 bug**：`八卦山大佛.js` 的 7 次 `tint`
> 全部落空（`fz` 那個臉部 z 座標算錯），佛首的五官從來沒有畫上去過。沒動它——
> 不在這次範圍內，但那就是這類 bug 的長相：報告一片漂亮，東西不在。


### 兩支新的造型工具（`plate`／`revolve`）

從實際產出反推加的（`wwwroot/src/blueprints.js`，`module.exports` 也要跟著加）：

- **`plate(v, {pts, plane, at, w, t, c})`**——沿折線的薄片，立在 `'xy'`／`'zy'`／`'xz'`
  其中一個平面上。`limb` 是圓的、`box`／`cyl`／`taper` 只能軸對齊，所以「平的、彎的、薄的」
  那一類（閃電形尾巴、鰭、翅膜、爪、旗、招牌、握把）本來**沒有工具做得出來**。
  實測的病徵：皮卡丘的閃電尾拿 `box` 疊，疊出來是一片躺在 x–z 平面的鋸齒板（俯視圖一看就知道）。
  每一層都先拉一條 `v.line` 當骨幹，`w` 小的時候才不會斷成一截一截（跟 `limb` 同一個理由）。
- **`revolve(v, {prof, shell, c})`**——`[[半徑, 高度], …]` 繞 y 軸轉，轉折點之間線性內插。
  杯、瓶、碗、鐘、燈罩、香爐。以前只能一段段疊 `cyl`／`taper`，接縫是硬階、尺度一縮就對不齊。
  `shell` 只留外壁，**杯底自己補一片 `v.cyl`**（跟 `cyl` 的 `hollow` 一致）。

**代價**：用到這兩支的藍圖檔**不能再拿回 `參考/block-builders/` 那包 `file://` 版跑**
（`ReferenceError`）。使用者明確接受了這個代價（「這版不用考慮這麼多」），
所以〈`list.js` 為什麼還在〉那條「整包拿回去照樣能用」現在只對沒用到新工具的藍圖成立。

**下一個看得到的缺口：八角錐。** 目前沒有任何一支畫得出來，而模型的替代做法
（`hipRoof` ＋ `stampY(45)`）**疊出來是八角星不是八角形**——兩個正方形的聯集是星，
要八角形得取交集，而 `stampY` 只會疊上去。中式重簷、八角亭、方尖碑的收頭都會撞到。
還沒做——跟 `plate`／`revolve` 一樣要有實際產出當依據才動手。

### 撞名要當「必修」，不能放過去

`customBlueprint`（`:4589`）碰到名字跟現有藍圖相同會直接擋掉，**只留一行 `console.warn`，
整份藍圖靜靜消失**。而 `importBlueprint` 為了「貼上→改→再貼」的節奏會自動加編號，
所以驗證會過——但存出去的檔案內容裡那個 `name` 還是撞號的那個，遊戲載入時走的是真正的
`customBlueprint`。所以 `RenamedFrom` 有值時要當必修回饋給模型改名，`/api/blueprints/save`
也擋這件事。

### 產生器頁只給靜態圖；互動 3D 交接給預覽頁

`藍圖產生器.html` 顯示的是**靜態的四視圖 PNG**（`<img>`），不是 3D。刻意的：
那張圖就是 Gemini 看到的同一張，你評的跟它評的是同一個東西。
上面那一排「候選」也是同一件事的延伸——同一句話跑出來的幾個 sample 擺在一起比，
點一下就把整組內容（程式、報告、四視圖）換成那一個。換了之後
「已收進遊戲／已存成檔案」會**跟著失效**（`useCandidate()` 把兩個旗標歸零），
不然按鈕會顯示已存、實際存的是另一個候選。

想拖著轉、比 1800／9000 兩檔、自己跑體檢，按「🔍 在預覽頁打開這一版」——
產生器把程式碼寫進 `localStorage['block-builders/handoff']` 再 `window.open`
`藍圖預覽.html`，那一頁尾巴那段開場讀走、清掉、填進 `#paste`、`click('#load')`，
所以走的是跟人工貼上**完全同一條路**（`importBlueprint`）。
實測：新分頁自動載入、選單選中、蓋出 2990 塊、體檢自動跑完、交接鍵清乾淨、0 錯誤。

**不在產生器頁自己 init 一份引擎**：那要從 `藍圖預覽.html` 複製 `ENG.init`、清空場景那
十行 `put*([])`、`build()`、拖曳縮放、render loop 共約 60-80 行，等於同一件事兩份要維護，
而且只會做出預覽頁的半成品（沒有建材三檔、沒有只看輪廓、沒有下載四視圖）。

用 `localStorage` 不用 `sessionStorage`：`window.open` 開出來的新分頁雖然會繼承一份
sessionStorage，但那是**複製**、而且 `noopener` 之類的情況不保證，跨分頁不可靠。
（也因此那顆按鈕**不加** `noopener`。）

### 產生紀錄：每一份產出都自動落地

`generate`／`revise` 都不存檔，所以在這之前**藍圖程式只活在產生器那一頁的 JavaScript
陣列裡（`versions[]`）——關掉分頁就沒了**，只有四視圖 PNG 留在 `wwwroot/shots/`。
實際踩過：使用者跑出「中頭獎的樹懶」兩版，回頭想比對時只剩兩張圖、程式沒了。

所以 `BlueprintHistory` 在**每一輪**（含蓋不起來的、含自動重跑掉的中間輪）後面自動寫兩個檔：

| 檔案 | 內容 |
|---|---|
| `history/{目標}/{stem}.js` | 藍圖程式原文。**這個檔本身就是備份**——直接丟進 `blueprints/` 或貼進預覽頁都能用，不必透過這支服務才讀得回來 |
| `history/{目標}/{stem}.json` | 描述、意見、體檢報告全文、提醒、塊數、四視圖網址、kind（generate／revise／polish）、輪次、**帳單** |

**分「目標」資料夾**（`SafeName.Group()`＝藍圖的 `name`，解不出名字的進 `_蓋不起來`）。
分類鍵用 `name` 是因為後端補充第 4 條要求改版時**沿用同一個 name**，所以同一座建築的每一版
（含失敗的重跑輪、打磨前後）都會落在同一格。`shots/` 用**同一個資料夾名**，
所以 `shots/{目標}/` 與 `history/{目標}/` 裡是同一座建築的東西。
以前兩邊都是一大包平的檔案，跑十幾次之後就找不到哪張圖配哪份程式了。

**中間輪也存**（一條跑 3 輪的鏈會留 3 筆）。自動重跑掉的那幾輪最貴也最需要回頭查——
沒有它們的程式與錯誤訊息，「修復輪值不值得開 high 思考」就沒辦法判斷。
每一筆各自帶**那一輪自己**的帳單（`AttemptRound.Usage`），不是整條鏈的累計。

實作上有一個順序問題：**整條鏈要一起寫、不能每輪寫完就存**——中間輪當下還不知道
最後會叫什麼名字（名字要體檢過了才解得出來），寫不進正確的目標資料夾。
所以 `ProduceAsync` 把每一輪收在 `rounds` 裡，跑完（成功或全失敗）才呼叫 `WriteChainAsync`。

**帳單那兩格（`usage` ＋ `think`）要一起看**：沒有 `think`，改過設定之後就分不出兩筆
數字不同是題目不同還是旋鈕不同，A／B 就做不成。舊紀錄沒有這兩格（`null`），
前端那一行就不畫。量出來的數字整理在〈調校筆記〉1。

- **`{stem}` 跟四視圖的檔名完全一樣**（`shots/{目標}/{stem}.png` ↔ `history/{目標}/{stem}.js`），
  回頭比對時圖跟程式才配得起來。兩邊都走 `SafeName.Stem()` 與 `SafeName.Group()`——
  **這就是那支工具存在的唯一理由**，各自清洗一份就會在遇到怪名字時對不起來。
- `stem` 本身是全域唯一的（`{時分秒}-{名字}-c{候選}r{輪}`），所以 `ReadAsync()`
  **不信任前端給的資料夾**——直接在 `history/` 底下列出自己的檔案找那個檔名，
  目錄穿越從源頭就不成立。`TryLoadAsync()` 則要收前端傳回的 `shotUrl`，
  所以只取最後兩段、各自清洗、再確認解出來的絕對路徑真的落在 `shots/` 裡。
- 放在專案根目錄底下**不是** wwwroot：這是工作紀錄，不需要被當靜態檔送出去。
- **存不進去不能影響產生流程**：`WriteAsync` 吞掉 IO 例外只寫 log。紀錄是加分項，
  磁碟滿了不該讓使用者那一輪白跑。
- 產生器頁最下面那張「產生紀錄」卡列出最近 60 筆，點一下把那一版**載回工作區**
  （接在版本列後面，不覆蓋現在那一版），順便還原當初的描述——不還原的話按「再改一版」
  會拿現在框裡那句當目標，改出來是另一個東西。
- **參考圖存在 `history/{目標}/_ref/`**（`BlueprintHistory.WriteRefsAsync`），
  檔名是內容的 SHA-256 前 16 碼，所以**同一張圖只存一份**——同一個目標會跑很多版，
  用的通常是同一批圖，逐版各存一份會白白膨脹十倍（實測跑三輪、每輪帶同樣兩張，只存 2 個檔）。
  每一筆紀錄的 `refs` 記下自己用了哪幾張（各版用的圖不一定一樣）。
  **為什麼要存**：沒有它，回頭只比得出「產出跟它自己寫的那幾行註解像不像」，
  比不出**「跟真正的目標像不像」**——而後者才是使用者的標準。
  放 `history/` 底下不進 wwwroot（不會被當靜態檔送出去），要清就跟紀錄一起刪。
  **但載回工作區時不會自動還原到前端**（那要再開一條把圖送回瀏覽器的路），
  所以那一頁仍然會講「要繼續改就重拖一張」。
- **對照輪自己的帳單另記一格**（`CompareUsage`）。它原本只併進整次操作的總帳、
  回給前端顯示就沒了，事後答不出「對照輪到底多貴」「`CompareThinkingLevel` 降到 low 能省多少」。
- **改版記得從哪一筆來**（`FromStem`）。靠的是四視圖與紀錄共用同一個 stem，
  所以前端傳回的 `shotUrl` 就指得出上一版是哪一筆（`FromShot()`），不必另外傳一格。
  沒有它就只能照時間順序與名字猜同一條線上的前後版，「這一輪到底改了什麼」比不出來。
- 蓋不起來的那幾輪 stem 是 `{runId}-蓋不起來-c{no}r{輪}`，`ok: false`，
  `round`／`rounds` 標出它在鏈裡的位置，`error` 是載不進來時的訊息。
  一條鏈全部失敗時整條進 `_蓋不起來/`。
- 會累積（一份約 10–30 KB），要清就直接刪 `history/`。

`{stem}` 是前端傳回來的，所以 `ReadAsync()` 只取最後一段檔名、而且要求解出來的絕對路徑
真的落在 `history/` 裡（跟 `BlueprintShooter.TryLoadAsync()` 同一套防目錄穿越）。

### 收下一份藍圖有兩條路

| | 「✅ 收進遊戲」 | 「📁 另存成 blueprints/ 檔案」 |
|---|---|---|
| 存哪 | 這個瀏覽器的 localStorage | `wwwroot/blueprints/*.js` ＋ 重產 `list.js` |
| 誰做 | **純前端**，不呼叫後端 | `POST /api/blueprints/save` |
| 誰看得到 | 只有這台這個瀏覽器 | 每個開這個站的人；整包拿去 `file://` 也在 |
| 何時消失 | 清瀏覽資料、換瀏覽器 | 不會 |
| 管理 | 遊戲「📥 匯入建築」那張清單（可匯出／刪除） | 檔案系統 |

「收進遊戲」是寫進**遊戲自己的匯入儲存**，key 與格式都照 `src/game-ui.js:534-567`：
`localStorage['block-builders/bp1']` = `[{file, code, names:[…]}]`，
存的是**原始碼**不是格子（藍圖是會跟著建材檔位重畫的函式，存格子等於釘死在某一個大小）。
另外設計一套格式的話遊戲那邊讀不到，而且同一份東西會有兩套解析要維護。
兩頁同源，所以產生器寫的就是遊戲讀的（實測：寫入後開遊戲，`imported` 有它、下拉選單選得到、
蓋出 2990 塊、「匯入建築」清單也列出來附匯出／刪除）。

兩個細節：
- **同名要換掉、不能再加一筆**。遊戲載入時對每一筆跑 `importBlueprint`，撞到自己已匯入的
  同名那份會直接蓋掉（`blueprints.js:4719-4726`），所以留兩筆的結果是清單出現兩列同名、
  卻只有一座蓋得出來。
- 判斷同名用的名字是**從程式碼撈的**（`nameOf()`），不是那一版原本的名字——
  使用者可能在「藍圖程式」框裡手改過 `name`。
- 撞名的守門只在檔案那條路（`POST save` 會擋）。瀏覽器那條路不擋，因為遊戲載入走的是
  `importBlueprint`，它會自動加編號；跟「📥 匯入建築」的行為一致。

### `list.js` 為什麼還在

上游是 `file://` 直接開的，而 `file://` 列不出資料夾內容（`fetch` 被 CORS 擋），所以
`blueprints/list.js` 手動列檔名。有伺服器之後其實可以不用它，但**刻意保留**：這樣整個
`wwwroot/blueprints/` 資料夾拿回去 `file://` 版照樣能用，`index.html` 與 `藍圖預覽.html`
一行都不必改。存檔時由 `BlueprintStore.RegenerateListAsync()` 重產。

改它要守三件事：
- **抬頭沿用檔案裡現有那段**，不要重打——上游有 e2e 測試守著 `藍圖預覽.html` 的 `LIST_HEAD`
  與 `list.js` 的抬頭逐字相同
- **LF、無 BOM**（現有檔案就是這樣，`UTF8Encoding(false)`）
- 陣列格式與排序照 `藍圖預覽.html:676-704` 的 `bpFilesFrom()` / `listText()`：
  舊清單順序有意義（＝選單先後）所以照舊排前面，新檔案接在後面用 `zh-Hant` 排序

### 開發時靜態檔一律 `no-cache`

`Program.cs` 的 `UseStaticFiles` 在 Development 補了 `Cache-Control: no-cache`。
預設**一個 Cache-Control 都不送**，Chrome 就自己啟發式快取——結果是改了 `wwwroot`
裡的檔案、重啟站台、頁面卻還是舊的（實測踩過：`index.html` 加了一顆按鈕，
伺服器送的是新版，瀏覽器畫的是舊版，Ctrl+F5 才會出來）。
這個專案的遊戲本體整包都是靜態檔、改的頻率很高，所以這條是必要的。

`no-cache` 不是「不要快取」而是「可以存但每次都要驗證」，配上 ETag 還是回 304、不重傳
（實測：帶 `If-None-Match` → 304 / 0 bytes，不帶 → 200 / 27679 bytes）。
正式環境不加這條。

### VS F5 跑的是 IIS Express，不是 Kestrel

`Block-builders.csproj.user` 的 `ActiveDebugProfile` 是 `IIS Express`
→ 網址是 `http://localhost:55362`／`https://localhost:44368`，
不是 `dotnet run` 那組 5273／7053。給使用者網址前先確認他用哪一種啟動方式。

### 改 `index.html` 那張時鐘卡要小心寬度

`#time` 那張卡（🏅 成就／📥 匯入建築／🤖 AI 產藍圖）是 `display:block` 的 shrink-to-fit，
而 `<button>` 預設是 **inline-block**——**同一行的 inline 盒子在算 max-content 時是相加的**，
所以多一顆按鈕就把卡片撐寬一截。實測加第三顆後 193 → 290px，而 640px 以下 `#head` 只讓出
232px（見 `index.html:219-223` 那條 media query 的註解），390px 螢幕上會跟時鐘卡疊 86px。

`#aiBtn` 因此明確寫了 `display:block`：自己成一行，卡片寬度變成取各行的最大值，維持 193px。
**再加按鈕時要照做，並且量過再收工**（用 playwright 量 `#head` 右緣與 `#time` 左緣的間隙）。

`file://` 開的時候那顆按鈕**照樣顯示**，按了才用遊戲自己的 `toast()`（`game-save.js:62`）
講「要先 dotnet run」。原本寫成直接隱藏，但整包的玩法本來就是「雙擊 index.html」
（上游 README 第一段），那樣按鈕會無聲消失，找不到的人只會以為功能沒做出來。
要隱藏任何東西時用 `el.hidden` 而不是 `style.display='none'`——後者會蓋掉那條 `display:block`。

### 圖片格式看檔頭，不看 Content-Type

`BlueprintsController.SniffImageMime()` 認 PNG／JPEG／WebP／HEIC 的檔頭。
客戶端宣告的 `Content-Type` 不可信（實測 PowerShell 送真的 `.png` 也只給
`application/octet-stream`），而 Gemini 的 `inlineData` 要的是對的 `mimeType`。

### 思考分級，溫度要低（**修復輪的思考曾經設錯**）

使用者用手動網頁版的經驗：**開思考的時候明顯比較不會產出缺參數的藍圖**——
那正是體檢裡「`v.box(...)` 的第 7 個參數 `c` 沒給」那一類，也是修復迴圈最常在修的東西。

所以 `RepairThinkingLevel` 曾經設成 `low`（理由是「照報告修錯不必想很久」）**是錯的**：
**每一輪都要重新輸出整份藍圖**——連撞名那一輪的指示都是「只改 `name`，其餘不要動，
輸出完整的藍圖」——所以每一輪都同樣有「某支函式漏給參數」的風險。
在最該防缺參數的那幾輪把思考關小是反的，而且修復鏈跑完 4 輪失敗比一次高思考貴得多。

**但「一律 high」也不對**：思考是最貴的一格（見上一節）。現在分三格，
由 `BlueprintGenerator.FirstTune()` 決定第一輪、`ProduceAsync` 決定重跑輪：

| 這一輪在做什麼 | 設定 | 預設 | 降過頭會怎樣 |
|---|---|---|---|
| 第一版 | `ThinkingLevel` | `medium` | 細節少一點，**使用者看四視圖就看得出來** |
| 再改一版／自動打磨 | `ReviseThinkingLevel` | `medium` | **可能安靜地把上一版的部件簡化掉**（見下） |
| 蓋不起來、自動重跑 | `RepairThinkingLevel` | `high` | 這是保單，不要動 |

兩個 medium **同值但分開放**，因為降下去的風險完全不同——見最後兩段。

降級的依據（數據在〈調校筆記〉1）：

- **實際跑過的每一筆都有參考圖**，純文字的一筆都沒有。所以「第一版是從零規劃」站不住：
  它手上永遠有圖、有量好的色盤、有兩萬多字的規格。
  **這也是為什麼沒有做「有圖才降」的條件分支**——有圖就是 100% 的流量，那條分支永遠成立、
  另一條永遠不會被走到，等於把「降預設」寫成一條死路加一條活路。
- 降級前的成績（92% 第一次就蓋得起來、「缺參數」一次都沒發生）是
  「有圖 ＋ 量好主色 ＋ high」量出來的。它證明這個組合很穩，
  **但沒有證明那 92% 是 high 買來的**。
- 實際的 revise 意見長這樣——「加個手銬好了」「手銬換個顏色吧 看不出來」。
  都是一句話的局部修改，卻要重吐整份 8 KB 藍圖。

**`RepairThinkingLevel` 因此更不能動**：它是這個降級的保單。真的吐出缺參數的藍圖，
體檢會擋下來、自動重跑一輪，而那一輪照樣是 high。最壞情況是偶爾多一次呼叫。
**但它很貴**（一次 high 重跑 ≈ 兩次完整的第一版），所以要動它之前先看紀錄裡
那幾輪到底錯在哪——中間輪現在有存了。

**但那張保單保不到 `ReviseThinkingLevel` 再往下的風險**，所以那一格不要動到 `low`：
revise 每一輪都要重吐整份藍圖，思考太低時它可能**安靜地把使用者原本喜歡的部件簡化掉**——
`fails` 只擋載不進來、⚠ 只擋東西沒畫上去，**沒有任何一條檢查抓得到「它把東西拿掉了」**，
只有使用者看四視圖看得出來。第一版沒有這個風險（本來就沒有前一版可以弄壞）。

要驗有沒有降過頭：產生紀錄裡每一筆都寫了 `think`（當時哪一格）與 `usage`（那一條鏈的帳單），
拿同一句描述在兩個等級各跑一次就比得出來——「載回工作區」會還原當初的描述，對照組是現成的。

溫度另一個方向：產藍圖是「照一份規格產出必須跑得起來的程式」，
**溫度高換來的不是創意，是漏參數與算錯座標**，所以壓到 0.2（修復輪也是 0.2）。
曾經是 0.35，那個高度是留給「候選之間要有差異」的；候選預設關掉之後那個理由就沒了。
**注意溫度不是成本旋鈕**——它不改變 token 量，降它省到的只是「少出錯→少觸發重跑」。

那候選之間的差異從哪裡來？**從明講的「取向」，不是從溫度亂數**
（`BlueprintGenerator.Angle()`）：第 1 個不加話（照說明書的判斷做）、第 2 個往部件數壓、
第 3 個往輪廓比例壓。三段都是說明書自己講過的事，只是把重心挪一挪，不會跟規格打架。
這樣拿到的是三個真的不同的做法，三張圖擺在一起比才有意義——
同一個做法擲三次骰子，比出來的只有雜訊。
（修復輪不帶取向：`RepairPrompt` 是從 `goal` 重建的，那一輪的工作是把錯修掉，
而取向已經體現在它正在修的那份程式裡了。）

`Model` 預設 `gemini-3.8-flash`（使用者指定）。**已經打通**——`wwwroot/shots/` 裡有使用者
自己跑出來的產出（皮卡丘、日本咖哩塊、樹懶踩到黏鼠板…），那些只有真的呼叫成功才會產生。
之後若打不通，先去 Google AI 的模型文件對現在叫什麼，改設定即可，不用改程式。

### 模型與思考強度可以在產生器頁上挑

那一排狀態 pill 裡有三個下拉：**模型**（選項來自 `Gemini:Models`）、**思考**與**改版**
（都來自 `Gemini:ThinkingLevels`）。只有一個選項時退回純文字，不擺假的控制項。
`generate` 帶 `model`／`think`／`reviseThink`（它可能跑到自動打磨，那一輪走改版那一格），
`revise` 帶 `model`／`reviseThink`。所以改到一半換個模型或思考強度再試是可以的。

三個值一起包成 `RunTune` 傳進產生器，每一格 null 就退回設定值——所以
`RunTune.Default` ＝完全照設定跑，跟加這個功能之前一模一樣。

**自動重跑那一輪的思考強度（`RepairThinkingLevel`）刻意不開放**：它是前兩格降下去之後的
保單（漏參數的藍圖由體檢擋下、由那一輪以 high 重修），讓人在頁面上關掉保單，
等於讓另外兩格的下修變成沒有底。要動它只能改設定。
改版那一格的下拉有 `title` 提醒「不建議調到 low」——理由見 `ReviseThinkingLevel` 的註解
（思考太低時它可能安靜地把使用者原本喜歡的部件簡化掉，而沒有任何一條檢查抓得到）。

三件事是刻意的：

- **白名單，不是提示清單。** 模型名字會被插進 `/v1beta/models/{model}:generateContent`
  的路徑，收前端的自由字串等於讓外面的人決定要打哪個網址；思考等級送錯值 API 會回 400。
  `GeminiOptions.ResolveModel()`／`ResolveThink()`
  只認逐字對得上的，對不上一律退回設定值（**不是報錯**——那是設定問題不是使用者的錯，
  而且為它中斷一次要跑好幾分鐘的產生不划算；實際用了哪一格會寫進產生紀錄，事後查得到）。
  `GeminiClient` 送出前**再過一次**同一支：保證「插進網址的字串出自白名單」這件事
  要在最靠近網址的地方成立，之後多一條呼叫路徑才不會漏掉。
  實測 `../../evil` 與不在清單的名字都退回預設。
- **整條鏈共用同一個模型**（第一版、自動重跑、自動打磨）。混著用的話那一份的帳單
  會是兩個模型的數字加起來，之後分不出貴在哪——所以模型跟溫度、思考強度一樣掛在
  `GeminiTune` 上，重跑輪只換後兩者、模型沿用 `first.Model`。
- **產生紀錄要記模型**（`HistoryHead.Model`，跟 `Think` 並列）。理由一模一樣：
  沒有它，兩筆 `Usage` 差很多會分不出是題目不同、旋鈕不同還是模型不同，A／B 就做不成。
  產生器頁的帳單那一行會把它印出來；舊紀錄沒有這一格就不畫。

## 版本控管注意

此目錄**不是 git repo**（`參考/block-builders/` 裡面那個是上游自己的）。沒有 `.gitignore`。
要初始化 git 的話先排除：`Block-builders/obj/`、`Block-builders/bin/`、`.vs/`、`*.csproj.user`
（產物），以及 **`Block-builders/gemini.key`（金鑰）**、`Block-builders/wwwroot/shots/`（產出的圖）、
`Block-builders/history/`（產生紀錄）。
